Dharmesh Shah：Latent Space 播客——代理网络与 MCP

HubSpot CTO 谈混合团队、WaaS vs RaaS、代理间记忆共享与 MCP 开放标准
来源：Latent Space: The AI Engineer Podcast · 2025-03-28 · 嘉宾：Dharmesh Shah
📌 核心观点
推 1 · 混合团队：人类+AI agent 的协作模式

Dharmesh 在 Latent Space 播客上提出了一个核心概念：混合团队（Hybrid Team）——不是"人用 AI 工具"，而是"人和 AI agent 组成同一个团队"。区别在于角色和责任：人类负责判断和关系，agent 负责执行和数据。

他举了一个例子：一个销售团队由 3 个人 + 2 个 agent 组成。Prospecting Agent 负责找线索、发邮件、预约会议。Guided Sales Agent 负责分析 deal 风险、推荐下一步。3 个人类销售负责 谈判、关系建立、签约——这些是 EQ 密集型任务。agent 负责执行密集型任务。

他说这个模式的关键不是"省人头"而是 "让人做人擅长的事，让 agent 做 agent 擅长的事"——如果反过来，既浪费了 agent 也浪费了人。

推 2 · WaaS vs RaaS：商业模式辩论

播客中最有争议性的一段是 Dharmesh 对 WaaS（Workforce as a Service，代理即员工） vs RaaS（Results as a Service，结果即服务） 的辩论。他说 RaaS 被过度炒作——"按结果收费听起来很性感，但 定义'结果'比定义'用量'难得多。"

他的论据是：WaaS 把 AI agent 当员工——按"工作时长"或"任务量"收费，类比人力外包的定价模式。RaaS 按"产出结果"收费——按线索、按解决率。问题是很多"结果"是多因性的——一个 deal 赢了是销售、产品、市场、运气的组合，你怎么归因到 agent？

他说："RaaS 适合 单因性结果——比如客服解决率（基本只看 agent）。不适合 多因性结果——比如销售成交（太多变量）。HubSpot 后来做的结果定价只选了单因性的场景，就是这个原因。"

推 3 · MCP 作为开放标准的重要性

Dharmesh 在播客中重点谈了 MCP（Model Context Protocol） 作为开放标准的重要性。他说 MCP 的价值不是"又一个 API 标准"，是 "让 AI agent 能跨系统获取上下文的通用语言"。没有 MCP，每个 AI 工具要对接一个 SaaS 就要写一个专属集成——N × M 的复杂度。有了 MCP，变成 N + M。

他说 HubSpot 做 MCP 服务器的动机不是"开放"而是 "必要性"："如果我们的客户用 ChatGPT 问'我上个季度哪些 deal 有风险'，ChatGPT 需要 CRM 上下文。如果 MCP 不存在，客户要么手动复制粘贴数据（荒唐），要么用一个专属集成（太重）。MCP 让任何 AI 工具都能即插即用地读 CRM。"

他还给了一个判断："MCP 会成为 AI 时代的 HTTP"——一个所有人都用但没人注意的基础设施。

推 5 · Dharmesh 作为技术 CTO 的视角

在 Latent Space 上，Dharmesh 展示了他作为 技术型 CTO 的一面——不同于在 TEDxBoston 上的哲学性演讲，这里他谈的是架构决策。他谈了为什么 HubSpot 选择把 MCP 作为生产级标准推出而不是等行业标准成熟，谈了代理间记忆共享的工程挑战，谈了 AI 辅助编程如何改变 HubSpot 的研发流程。

他说："我做 CTO 25 年，技术变化经历了几轮——云计算、移动、SaaS。但 AI 对软件工程的影响是最大的一轮——因为它改变了谁写代码、写什么代码、代码怎么维护。"

💬 行业
推 6 · 代理间记忆共享的挑战

Dharmesh 在播客中深入讨论了一个被行业忽略的技术难题：代理间记忆共享。他说当一个团队有多个 agent——Sales Agent、Service Agent、Data Agent——它们各自有对话记忆和上下文。但当一个 agent 接手另一个 agent 的工作时，记忆怎么传？

他说这个问题的工程难度在于：一、记忆不是数据——数据可以存在数据库里共享，但记忆是情境化的，脱离上下文就无意义。二、不同 agent 的"记忆格式"不兼容——Sales Agent 记的是"客户提到预算紧张"，Service Agent 需要的是"客户工单优先级"。

他说 HubSpot 的解法是 共享上下文层——所有 agent 从同一个 CRM 上下文获取信息，而不是各自维护记忆再互相传输。"代理不需要共享记忆，它们需要共享 真相源（source of truth）。CRM 就是这个真相源。"

推 7 · AI 辅助编程如何改变软件工程

Dharmesh 在播客中谈到了 AI 辅助编程对 HubSpot 研发的影响。他说变化分三个层面：一、写代码——AI 从辅助补全到生成完整函数。二、读代码——AI 可以快速理解陌生代码库。三、测代码——AI 自动生成测试用例。

但他说最重要的变化是 "谁写代码"：以前只有工程师能写代码。现在产品经理、设计师甚至运营可以用自然语言"写"代码——描述功能，AI 生成。这意味着工程团队的角色从"写代码"转向了 "审代码和设架构"。

他说："我不担心 AI 替代工程师。我担心的是 不使用 AI 的工程师被使用 AI 的工程师替代。"

推 8 · 代理市场的早期信号

Dharmesh 在播客中分享了他对代理市场早期信号的分析。他说 agent.ai 的数据揭示了几个有意思的模式：一、内容类代理最先被用起来——博客生成、社媒文案。二、数据类代理增长最快——数据查询、分析、可视化。三、决策类代理最少——因为可靠性还不够。

他说："这个分布跟 80 年代软件业一样——先有文字处理，再有数据表格，最后有决策支持系统。AI 代理在 重演软件史，只是速度快了 100 倍。"

📦 公司
推 9 · HubSpot 的技术哲学：开放优先

Dharmesh 在播客中阐述了 HubSpot 的技术哲学：开放优先（open-first）。他说这不是理想主义——是商业判断。"AI 时代，封闭系统的价值在缩小。因为 AI agent 天然需要跨系统获取上下文。如果你的数据是封闭的，agent 用不了你的数据，你的价值就归零。"

他举了一个例子：HubSpot 做 MCP 服务器不是"把数据给别人"，是 "让客户的数据在客户选择的 AI 工具里可用"。数据所有权属于客户——这是设计原则。

推 10 · agent.ai 的内部定位

Dharmesh 在播客中谈到了 agent.ai 在 HubSpot 体系内的定位。他说 agent.ai 不是 HubSpot 的子产品，是 HubSpot Labs 的独立实验——独立品牌、独立用户、独立技术栈。这样做的目的是让它像创业公司一样快速迭代，不被大公司流程拖慢。

他说："如果 agent.ai 在 HubSpot 内部做，要走产品评审、安全审批、品牌对齐。这些流程是对的——对成熟产品。但对实验产品是 创新杀手。独立运作让它 3 个月冲到 258,000 用户——这是大公司流程做不到的速度。"

🧩 产品
推 11 · 细粒度数据权限控制

Dharmesh 在播客中讨论了一个非常技术化的问题：AI agent 的数据权限控制。他说这比传统 RBAC（基于角色的访问控制）复杂得多——你需要控制"agent 能看到什么数据"、"能修改什么数据"、"能基于什么数据做决策"。

他说 HubSpot 的设计是 "类似 OAuth 但更精细"——OAuth 控制的是"应用能不能访问你的数据"，HubSpot 控制的是"agent 能不能基于你的数据做某个动作"。比如一个 Customer Agent 可以看客户历史但不能修改交易金额。

他说这个权限系统是 代理可靠性的基础设施——"如果权限控制不够细，agent 出错的风险就不可控。结果定价就做不到。"

推 12 · 代理的可靠性工程

Dharmesh 在播客中谈到了代理可靠性工程的方法论。他说 HubSpot 内部把可靠性分为三层：输出层（agent 说的内容对不对）、行为层（agent 做的动作对不对）、后果层（agent 的行为有没有造成不好的后果）。

他说最难的是后果层——"一个 Customer Agent 说了正确的话、做了正确的动作，但如果客户不满意，这个交互还是失败的。" 衡量后果层的方式是 客户反馈——每次代理交互后自动收集满意度。

"72% 解决率不是我们测的，是 客户用脚投的——满意了不投诉，不满意了升级人工。这个数字比我们内部的质量评分更真实。"

推 13 · 代理的"记忆"设计

Dharmesh 在播客中详细讨论了代理的记忆设计。他说 agent 的记忆有三种：对话记忆（单次对话的上下文）、用户记忆（跨对话的用户偏好）、组织记忆（跨用户的公司级知识）。

他说 HubSpot 的设计选择是：把组织记忆存在 CRM 里，不在 agent 里。这样所有 agent 共享同一份组织记忆，不会出现"Sales Agent 和 Service Agent 对同一个客户有不同记忆"的不一致。对话记忆和用户记忆则在 agent 层维护——因为它们是个性化的。

"这个设计的核心是 真相源唯一——组织级的事实只存在 CRM，agent 只读不改。agent 修改组织记忆需要通过 CRM API，有审计日志。"

🏗️ 组织
推 14 · 域名投资的效率市场理论

Dharmesh 在播客中谈了一个有趣的题外话——域名投资。他个人是域名投资人，买了几百个域名。但他说域名投资是一个 "效率市场"——好域名都被估了，你很难找到低估的。

他用这个例子来类比 AI 市场："AI 领域也是效率市场——大家都在看同样的模型、同样的数据、同样的论文。你很难靠'我知道一个别人不知道的模型'赢。你能赢的是 '我有别人没有的数据'——对 HubSpot 来说就是 20 年的 CRM 上下文。"

推 15 · 工程师的 AI 转型

Dharmesh 在播客中谈到了 HubSpot 工程团队的 AI 转型。他说最大的挑战不是技术学习——工程师学新工具很快。最大的挑战是 "认知切换"——从"我写代码解决问题"到"我描述问题让 AI 写代码"。

他说："工程师最大的惯性是 '我自己来'——因为自己写更快。但这是短期正确、长期错误。今天 AI 写的代码可能比你慢，但明天会比你快。如果你今天不练'描述问题'的能力，明天就跟不上了。"

推 16 · 创始人文化的价值

Dharmesh 在播客最后被问到"为什么你还在 HubSpot"——作为一个已经财务自由的联合创始人，他完全可以选择退休。他的回答揭示了一种独特的创始人哲学："创始人留在公司不是因为需要钱，是因为对公司有好奇心"。

他说他每天来上班的原因是想知道"AI 代理到底能做到什么程度"。agent.ai 是他的好奇心产物，不是公司指令。"如果有一天我对 AI 不好奇了，我就会走。但 现在好奇心比公司还大。"
