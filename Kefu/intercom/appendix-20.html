Fin × Linear: Delivering High Quality AI Experiences

来源：Intercom 伦敦线下活动（2026 年 3 月）· Brian（Intercom 产品）× Matias（Linear 工程师）· 组织：Laura Secat

📌 一句话总结
推 1 · 核心结论

「高质量 AI」双视角对谈：AI 质量 = 宏观指标 + 单条对话的原子级迭代——Fin 度量分层（resolution rate 软 → hard resolution 最可靠 → CX/CSAT 主观但用户视角 → LLM 判幻觉率）；Linear 是非指标驱动文化的反面样本，但 AI 组正在重塑它。

双方共识：一切最终回到「读单条对话/trace」——「原子单位是对话，你永远无法完全离开它」；信任靠小爆炸半径渐进建立；把自家工具给客户（客户正在变成工程师）；UI 未来：软件形状剧变——越来越多软件是给 agent 用的。

👤 访谈人背景
推 2 · 录制信息

录制时间/地点：2026 年 3 月，伦敦（线下活动 + 观众 Q&A）；时长约 50 分钟。

组织：Laura Secat（Intercom 客服 QA 与持续改进项目经理，Fin 自家客服）；嘉宾：Brian（Intercom 产品，在司 12 年、近 3 年专注 Fin）、Matias（Linear 软件工程师，主做 Linear Agent）。

推 3 · 素材定位

全系列首次「产品方 × 另一家 AI 产品公司」双视角对谈——Intercom（客服 agent 供应商，自家就是 Fin 标杆客户）× Linear（给开发者做 agent 产品、「自己挠自己痒」）。

与第 16 篇（可观测性工程案例：TTFT/成本注入）互补：那篇讲 Fin 内部 trace，这篇讲两家公司对「质量循环」的完整方法论。

💬 行业
推 4 · AI 质量的定义：数字 + vibe

「高质量」一半是量化指标，一半是vibe：你给 agent 任务、它按你预期的方式完成且一致可靠——「难以用数字捕捉，但你见到就知道」。

Fin 质量度量分层：①resolution rate（是否转人工，仍有点软）→ ②hard resolution（用户明确回「答对了」，最可靠）→ ③CX/CSAT（主观但终端用户定性）→ ④LLM 判幻觉率/guidance 遵循（最难）。

推 5 · 指标即 trade-off（记忆与延迟的反直觉）

Fin 加记忆功能——解决率反而掉 0.5%，直接回滚没再上：「当然 agent 应该有记忆，但数据说不行」。

latency 反直觉：太快反而让人不信任（「怎么可能这么快就弄明白」）——曾需要人为拉高延迟又降回来；voice 要极快、chat 可耐心、email 完全无所谓。

Linear：不跑 AB 测试，「体验由架构方式决定」；真正权衡是「在仍感觉交互式的延迟内做到够好的质量」。

📦 公司
推 6 · 两种组织文化碰撞

Intercom：大规模下以gold benchmarks + 全量 AB 测试驱动——「AI 不可预测，必须看它如何影响指标」；AI 组（rigor/科学/全测试）与产品组（客户直觉）是两个独立 R&D 组织的张力。

Linear：隐私敏感——opt-in 反馈 + 标记好/坏对话；「很多人用且没人关掉」是合理信号；新手段：让 agent 自己报告「用户要求了但它做不到的事」——直接变成功能 backlog（发现用户未预见的用法）。

推 7 · 信任：多年度旅程与晴雨表

信任不是「信不信 agent」，而是「你信任 agent 去做什么」——Linear 的 triage intelligence 给足 guidance 后，用户愿意逐步授权自动化；建立信任靠小爆炸半径：先让 agent 展示能力、不碰危险的事。

Intercom 信任 barometer：involvement rate（多少比例对话交给 Fin）；工具链递进：透明 → CX score → CX score reasons → Monitors 完全自定义——取舍：「CX score 我们控制 rigor，客户自定义归客户」。

🧩 产品
推 8 · 给客户我们自己的工具：客户正在变成工程师

Fin 的定位：「几乎要把它当作软件开发生命周期来思考」——客户从使用者变成「用我们软件做自己产品的工程师/产品人」。

Procedures + Simulations：simulation 用三个 LLM 角色（扮演终端用户 → 应用你的规则 → 当裁判评估）——Intercom 内部就是这么干的，现在暴露给客户迭代到有信心。

Linear 的code review / diff 产品：agent 产出 diff、人类评论并 steer——「跟 agent 协作坍缩成『看 diff → 评论 → 引导方向』」，减少上下文切换。

推 9 · 人类监督的滑动标尺

取决于底层模型能力 + 代码库是否便于 agent 迭代；从「完全放手」到「两人签字」都是合法端点——「监督是滑动标尺，随 agent 变强而移动」。

审查方式会变：逐行 review → review preview build / 验证能不能跑；产品要「逐步拆掉『批准 agent 输出』的障碍」。

「人-人协作」隐喻成立但差一块：agent 没有持久学习（记忆 flaky/fuzzy）——要么等模型原生解决，要么用 harness/skills/tools 把知识「写下来」（Memento 贴纸条比喻）；Anthropic 警告：「别建太多脚手架，模型会拆掉它」。

推 10 · 可观测性：为什么「读 trace」无可替代

最有趣的时刻：agent 犯的错「人类永远不会那样错」（如 Fin 深植在模型里反复说「请联系客服」——各种 hack 压不住，直到自研模型 CX Apex 才可能根治）——需要「对 agent 有 theory of mind」。

迭代小循环是未来：identify → understand → change → test（回放/模拟/backtest）→ validate；「微改进」的验证点仍是开放问题（可能就 10 段对话的小样本难在公共指标上验证）；锚点指标仍是 resolution rate/CX/CSAT。

人类读 trace 的时间：「很多——有日子半天都在盯 trace」；原子单位是对话，「你永远无法完全离开它」；Linear 零 bug 政策延伸到 agent：7 天内修完能修的 misbehavior。

🏗️ 组织
推 11 · 给客户可定制性的边界

客户用文本即可定制工作流（triage automations：路由/研究/翻译）——「整个功能就是定制」，每月跑几百上千次；因此要把我们自己的工具（指标 + trace 内省）给客户，让他们改进自己的 prompt/指令。

边界在移动：「agent 没设计来干这个、你该用 integration」的线，随模型变强持续外移——保持 stance 灵活，但承认有不该让 agent 干的事。

💡 UI 的未来
推 12 · 软件形状剧变

Linear：信息消费型 UI 仍不可替代（比 AI 文字墙密度高）——方向是「建一个 agent 能往里填信息的 UI，而不是让你自己解析文本」；操作类工作流会大量被 prompt 取代。

Brian（更激进）：软件形状在变：谁在用（人→agent）、为谁建（越来越为 agent 建）、在哪发生——「刚把 Monitors/Procedures 的 UI 磨到极致，但我真在问：这是不是已经过时了？」「很多 UI 会被冲走，剩下 monitors、基础报表、基础列表」；agent-driven 产品导览：「agent 为什么要解释？它应该直接做」。

「任何人对软件形状有信心都可能是过度自信」——已有客户「三个月没人登录 Linear」（standup 转录 → agent 建 ticket；MCP + claw 循环自动匹配 PR）——「假设 agent 会消费你的 primitives（API-first 升级版）」。
